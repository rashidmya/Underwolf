Production input commands now carry ordered snapshots: tag `0x118` is visibility plus state sequence; `0x119` is a capture request plus its visibility. The shared state layout and legacy worker remain unchanged. Input-capable DLLs do not infer command ordering from coalesced legacy bells.

Registration and cursor restoration use optimistic transactions: overlapping game calls pass through and publish successful intent; an interfered restoration cannot acknowledge completion and retries with that intent. Overlapping successes are ordered by atomic publication. This guarantees convergence after quiescence, not atomic OS state across concurrent native calls. Registration descriptors pack the [32 significant bits of Windows handles](https://learn.microsoft.com/en-us/windows/win32/winprog64/interprocess-communication) with flags. Cursor rectangles use `portable-atomic` 1.15.0; installation requires [`AtomicU128::is_lock_free()`](https://docs.rs/portable-atomic/1.15.0/portable_atomic/struct.AtomicU128.html), so hook paths never use its lock fallback.

Window destruction retains owner-thread dispatch while restoration is pending. A retained thread handle and nonblocking termination check distinguish a live owner queue from a terminated one; old queue cursor/count intent is never replayed onto a new queue. Replacement capture still requires a fresh request and healthy lease.

An initial parallel Wine run had colliding `xvfb-run -a` displays. Its incomplete helper/launcher logs are not passing evidence. The reruns use explicit displays 177 and 178. Cleanup only killed the test-owned process groups and their private Wine prefixes.

The probe uses deterministic command-line scenarios rather than a stdin JSON controller. `input_sender.exe` is a separate process for the end-to-end backpressure scenario. Individual adapter scenarios use native `SendInput` in the fixture; they do not fake hook outputs. Unit failure injection covers MinHook transaction rollback. A complete real-OS failure injection matrix is not claimed.

## Live failure and export-address correction — 2026-10-25

The first fresh run used Deadlock ClientVersion 6819, Proton `proton-11.0-2e-x86_64`, KDE Wayland, RTX 4090 driver 615.78.08, and a 2560 × 1440 client. GNU imports such as `GetRawInputBuffer as *const ()` pointed to jump stubs in `uw_overlay.dll`, not the shared system export. MinHook patched those stubs; SDL3's calls through its own imports bypassed them. The original same-module probes therefore did not prove interception across module boundaries. - `export-clippy.log` and `export-portable.log`: affected Windows code passes Clippy with warnings denied, and portable input/startup tests pass.

The correction resolves actual exports with [GetProcAddress](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress), matching [MinHook's API-target resolution](https://github.com/TsudaKageyu/minhook/blob/master/src/hook.c). The same address is used for creation, publication, enabling, and rollback. Missing exports fail installation. The owner retested the corrected DLL in a fresh game and reported that capture works. This closes the reported mouse-isolation failure; it does not cover the remaining live matrix.

This runs only with the verified `UW_SPIKE_CAPTURE=win32` drawing-only mode; it never starts C2 capture or the C3 injector. The legacy 14-pixel decorative cursor is parked outside the viewport before dimming starts, retaining the native cursor. Eight receiver tests, a clipping-geometry test, five bridge-control tests, and the real renderer smoke check passed. The owner replied “OK” to the fresh-run dimming and pointer check, which also requested a held left-Ctrl+Tab entry and right-Ctrl+Tab exit. | ShowCursor / cursor shape | Count and shape belong to the owner's input queue. Independent threads pass through; attached threads sharing focus use owner intent. | Release | Atomic permission clears independently; queued OS restoration occurs on owner thread, failed cursor operations remain pending | Lease, stalled UI, overflow and backpressure checks |

Cursor thread semantics follow [Microsoft's cursor documentation](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/menurc/about-cursors.md) and [ShowCursor's per-thread/attached-queue behavior](https://devblogs.microsoft.com/oldnewthing/20091217-00/?p=15643).
